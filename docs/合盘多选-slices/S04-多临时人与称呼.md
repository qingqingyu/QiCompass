# S04 多临时人 + 可选称呼 + 兜底名

- **类型**: AFK
- **Blocked by**: S01
- **覆盖决策**: D2（临时输入可多个）/ D6（临时人不建 UserSnapshotLink；显示名 = 会话内称呼 / 跨启动「对方+出生日期」）
- **Parent**: `docs/合盘多选设计决策.md`

## What to build

名单 `.temp` 类型从 S01 的「1 条」扩为「多条」，并落地临时人显示名策略：

1. **多临时人**：配置页「添加临时对方」入口（复用现有 tempInputForm 字段：出生时间/性别/城市/经度），每添加一人成为名单一条；列表展示已添加的临时人，可逐条移除
2. **可选「称呼」字段**：临时表单加可选文本字段（默认空）。填了 → 会话内显示称呼（如「相亲对象甲」）
3. **跨启动兜底名**：无称呼的临时人，卡片显示 `「对方」+ 出生日期`（从 ChartSnapshot.birthSolarTime 读；计算完成后回填）
4. **上限 8 合计**：存档勾选 + 临时人共同计入上限（S01 的校验扩展覆盖）
5. **resolved contentHash 写入名单**：临时人首次计算后，把隐式落地的 contentHash 记到该 RosterEntry（为 S05 增量预查与 S06 持久化铺路）
6. **红线——不建 UserSnapshotLink**：
   - 保持现状「模式 B 隐式落地只写 ChartSnapshot 不写 link」语义（`CompatibilityOrchestrator.swift` 现状行为，不改）
   - 零 SwiftData schema 演化、零 SyncManager 影响、ProfileView/命主卡零改动

## Acceptance criteria

- [ ] 配置页可添加 2-3 个临时人（各自独立出生信息），名单与勾选存档混排
- [ ] 有称呼的临时人 → 卡片显示称呼；无称呼 → 显示「对方 + 出生日期」
- [ ] 移除临时人入口正常；混合名单上限 8 计入临时人
- [ ] 临时人计算后：名单条目获得 resolved contentHash；SwiftData 中断言无该临时人的 UserSnapshotLink
- [ ] 杀 app 重启后（S06 前）：临时人以兜底名出现在（当时的）名单里不崩（正式恢复语义由 S06 完成）
- [ ] 测试：多临时人名单构造、显示名解析（称呼 → 兜底名）、上限 8 混合计数

## 实现锚点（现状快照 2026-08-13，实施以代码为准）

- `Features/Compatibility/CompatibilityViewModel.swift:62` — `tempBirthDate` 等单临时字段 → 改为 `[RosterEntry]` 内 `.temp` 结构体数组
- `Features/Compatibility/CompatibilityConfigView.swift:100` — `tempInputForm` 改为「添加临时对方」列表 + 逐条表单（含称呼字段）
- `Services/CompatibilityOrchestrator.swift:73` — 模式 B 隐式落地 ChartSnapshot（无 link）逻辑不改，resolvedHash 回填在 VM 层接
- `Models/UserSnapshotLink.swift` — 不触碰

## 红线与约束

- **D6 红线**：任何 slice 不得为临时人建 UserSnapshotLink；违反需重新征求用户意见
- **D4/D12 红线**：付费/后端零改动
- **i18n**：文案跟随现状中文硬编码（兜底名「对方」亦是）
- **错误显式传播**：临时人表单校验（出生时间未来/城市空/经度越界）沿用现有校验链，逐条校验不静默

- 数据层断言：临时人计算后 `UserSnapshotLinkStore` 查询为空（link 未创建）
