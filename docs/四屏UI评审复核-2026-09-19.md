## 三、逐条详述

### 1. Tab bar 遮挡内容 —— ✅ 成立(代码实锤)

评审者观察:「我的」页 `Why trust it` 被切、「深度」页第柒章被压住,判断为四屏通病、滚动容器缺底部 inset。

**复核**:属实,且成因明确。

- `ios/QiCompass/QiCompass/Features/Profile/ProfileView.swift:109` → `.padding(.bottom, 24)`
- `ios/QiCompass/QiCompass/Features/DeepAnalysis/DeepAnalysisHomeView.swift:74` → `.padding(.bottom, 18)`

两处 `ScrollView` 均**仅靠固定 bottom padding**,全项目未见 `safeAreaInset(edge: .bottom)` 或 `contentMargins` 处理悬浮 tab bar。悬浮胶囊 tab bar 实际占用约 90pt,18/24pt 显著不足。

「四屏通病」的判断也正确 —— 这是 `ScrollView` 的共性写法问题,不是单页 bug。

---

### 2. `Clashes: 寅` 胶囊换行 / 3. 竖排喜忌被裁 —— ✅ 成立(仅截图判断)

- 第 4 屏右上胶囊显示为 `Clas` / `hes:` / `寅` 三行,宽度计算未覆盖英文长词场景
- 第 3 屏右侧竖排「喜 水木火 / 忌 金土」贴右边缘,末字被裁

**诚实说明**:这两条我**只核对了截图,未定位到具体布局代码**。结论基于视觉证据,成因待查。

---

### 4. 合盘禁用按钮"透出另一层文字" —— ⚠️ 症状对,病因错

评审者判断:「明显的层级/透明度 bug」,下面透出了另一层文字。

**复核:不是层级问题。** 那行字是 CTA **自身的副标**:

```swift
// CompatibilityConfigView.swift:282
case .emptySelection: return "点选后即可排盘 · 名单上限 \(CompatibilityViewModel.rosterMax) 位"
```

禁用态下三个因素叠加导致它看起来像"透上来的":

| 因素 | 代码位置 | 值 |
|---|---|---|
| 整块前景色降级 | `:132` | `.foregroundStyle(cta.isEnabled ? onInkDeep : inkMuted)` |
| 底色降到三成 | `:137` | `inkDeep.opacity(0.3)` |
| 副标本身已是次级色 + 10pt | `:129-131` | `inkMutedSecondary` / `caption(size: 10)` / `tracking(1)` |

**影响**:若按评审者的病因去排查 z-order / 透明度叠加,会查空。真正的修法方向是**禁用态下单独提升副标对比度**(或禁用态不显示副标)。

### 6. 中英混排 —— ⚠️ 方向对,定性错(本份意见中代价差异最大的一条)

评审者原话:「既然做 diaspora-first,就应该是两套完整 locale 各自自洽,而不是一屏里两种语言打架」,并将其列为「最伤的一点」「结构性问题」。

**复核:方向认同,但定性错误,且错误的代价很高。**

**(a) 架构上你已经就是「两套 locale 各自自洽」了。**

不仅 UI 字符串走 locale,连命理词表都备了两份:

```swift
// DailyImageHeroSection.swift:274 / :288
static let mappingZh: [String: (yi: [String], ji: [String])] = [
    "七杀": (["果断", "担事", "攻坚"], ["犹豫", "树敌", "硬扛"]), ...
]
static let mappingEn: [String: (yi: [String], ji: [String])] = [
    "七杀": (["Decide", "Take It", "Push"], ["Waver", "Feud", "Overload"]), ...
]
// :321
private var isEn: Bool { AppLanguage.current == "en" }
```

**(b) 截图是 English 模式跑出来的,所以英文那一半是「正确输出」。**

`Do` / `Don't` / `Retry` / `Today's Reading` / `Why trust it` / `Clashes:` / `For reference only` —— 这些**全部是设计预期内的英文**,不是"混进来的"。

**(c) 真正坏的是反过来的那一半:该出英文却漏翻。**

`每日运势` / `命书生成失败` / `合盘` / `选择对方` / `还没有购买` / `我的` —— 这些是 **`sourceLanguage = zh-Hans` 的 key 在缺 en 翻译时的回退显示**。

实测 `ios/QiCompass/QiCompass/Resources/Localizable.xcstrings`:

```
总 key                 349
含中文且缺 en 翻译      142   (41%)
标记 needs_review        0
```

漏翻样例(节选):

```
每日运势 / 合盘 / 合盘 · 两人磁场合拍 / 选择对方 / 双人合盘 / 合盘解读
付费内容,解锁后可生成 / 剩余 %lld 次 / 24h 内已缓存,不消耗次数
一次买断 · 全设备同步 / 买断制 · 不含订阅 / 价格 %@,买断制,不含订阅
使用 Apple 登录 / 使用 Google 登录 / 加入名单 / 不建档案 · 填出生信息即可
%@ · 日主 %@ / 五行%@ · 日主%@ / 出生地:%@ / 双盘数据读取失败 …
```

**(d) 为什么这个定性差异重要。**

| 按评审者的定性 | 按实际病因 |
|---|---|
| 「双语策略是结构性缺陷」 | 「英文翻译覆盖率 59%」 |
| 要重新设计 locale 方案 | 补 142 条翻译 |
| 架构级返工 | 一次性体力活 |

评审者把一个 **i18n 覆盖率缺口**,误判成了**架构缺陷**。若照其框架行动,会对一个已经正确的架构做无意义返工。

**(e) 评审者结论中唯一站得住的部分**:「现在这个状态,中文用户觉得夹生,英文用户又读不懂一半」—— 对英文用户的描述完全准确,这正是 41% 漏翻的直接后果。

### 7. 今日页 AI 失败兜底 —— ✅ 成立,且应加重

评审者观察:Do/Don't 由规则引擎算出、本不依赖 AI,但 AI 段挂掉后整页主视觉位摆着红字「命书生成失败」。主张规则内容永远出得来、AI 降级为次级模块。

**复核:完全成立,且其依据比评审者陈述的更硬。**

宜/忌**不只是"不依赖 AI",而是纯客户端确定性查表**,连后端都不经过:

```
// DailyImageHeroSection.swift:267-268
/// 数据源(v1 简化,同前):前端十神→关键词查表,扩为**每列 3 词**;
/// 后续可挪后端基于喜忌+流日关系确定性映射(不增加 v1 后端复杂度)。
```

即 AI 完全不可用时,该页内容依然完整。当前却把 AI 的失败态渲染在首屏核心位置,使一个**实际正常工作的页面看起来是坏的**。

**判断**:此条优先级应与 Tab bar 遮挡同级。理由是它直接打击产品的核心主张 —— `CLAUDE.md` 定义的 Memorable Thing 是「专业不忽悠,不像算命软件」,首屏红字报错与该主张正面冲突。

### 8. 身份摘要不统一 —— ✅ 成立,但改法需调整

评审者观察:「我的」写 `1983 年生 · 癸亥`,「合盘」写 `1983-04-22 · 日主 庚`,主张选一个贯穿全 App。

**复核:现象属实,但「二选一」的处方需要调整。**

两者承载的不是同一信息:年柱(癸亥)是**生肖锚点**,日主(庚)是**命理主体**。两个页面的语境差异是真实的,直接砍掉一个会丢信息。

**倾向的方向**(非结论):统一为「生年 + 日主」的固定两栈一行,在所有页面用同一组件渲染,而不是各页选一个。

---

### 9. 「今日剩余 10 次」无解释 —— ✅ 成立

评审者观察:用户不知道自己在消耗什么。

**复核**:属实。附带发现 —— xcstrings 中**已存在**解释性文案 `24h 内已缓存,不消耗次数`,说明这个说明需求已被考虑过,只是未呈现在该屏。(该条同时也在 §三.6 的 142 条漏翻名单里。)

### 10. 付费红标 → 「第三章断在关键处」—— 🔶 直觉对,方案代价被严重低估

评审者主张:前两章完整可读,第三章给一段真实内容后断在关键处,其余收成单卡片。

**(a) 问题诊断认同。** 五个红标并排确实构成视觉上的「墙」。

**(b) 但所提方案与现有架构冲突,代价远超 UI 调整。**

付费拦截在**服务端**,客户端在无权益时根本拿不到付费内容:

```
// backend/app/api/interpret.py:211-239
base_module = entitlement_base_module(req.module)
entitlement = await run_in_threadpool(entitlement_store.get_active, ...)
if entitlement is None:
    → 403
```

因此「第三章给真实内容再截断」**无法由前端截断实现**,需要:新增 teaser module → 新 prompt 模板 → bump `PROMPT_VERSIONS` → 过 evalkit 回归(`CLAUDE.md` 强制,无 regression 才算完成)→ 过 `tools/check_prompt_sync.py` 三边一致。

这是**一个完整 slice 的工作量,不是调 UI**。且 `MONETIZATION.md` 于 2026-07-18 锁定过免费/付费分界,变更需重走决策流程。

**(c) 更便宜的等效方向**(非结论,供后续决策参考):问题不在"有红标",而在"六个红标并排"。将 M2–M7 从「每章各挂一个红标」收敛为**一张合并卡**(如「余六章 · 解锁全本」),红标只出现一次。视觉上的墙即消失,**零后端改动,不触碰已锁决策**。

### 11. 「我的」页重心错了 —— 🔶 同意一半

评审者主张:最大视觉块是登录卡,但登录收益只写了「跨设备同步」;而「不收集出生信息之外的任何资料」才是最有杀伤力的差异点,埋在小字里可惜。

**认同的部分**:隐私主张在命理这个品类里确实是强差异点,当前层级偏低。

**不认同的部分**:「登录卡不该是最大视觉块」的判断。在一个**有跨设备已购同步**的付费 App 里,登录正是防止用户换机丢失购买的关键路径 —— 它就该占据重心。

**倾向的方向**(非结论):保留登录卡体量,把隐私那句从小字**提升为卡内副标级**,而非削减登录卡。

---

### 12. Do/Don't 词太抽象 —— 🔶 同意,但归因与改法不同

评审者观察:`Take It` / `Push` / `Feud` 偏抽象,主张补一行具体语境。

**(a) 认同症状。** 对比同一条目的中英两版:

```swift
"七杀": (["果断", "担事", "攻坚"], ["犹豫", "树敌", "硬扛"])        // mappingZh
"七杀": (["Decide", "Take It", "Push"], ["Waver", "Feud", "Overload"]) // mappingEn
```

中文双字词自带语境,直译为英文单词后语义散失。**这是英文词表的质量问题,不是布局或信息架构问题。**

**(b) 不认同「补一行具体语境」的改法。** Do/Don't 双列的留白节奏是 2026-08-31 定稿的参考屏语言(`docs/design-ref/shuimo/`),加副标行会破坏该节奏,与 `DESIGN.md` 的克制原则冲突。

**倾向的方向**(非结论):重写 `mappingEn` 这 10 行词表,用更具语境的措辞(如 `Take the call` / `Avoid feuds`),在不增加行数的前提下解决语义散失。
