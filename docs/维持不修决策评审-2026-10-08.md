## A. M1-M7 翻译防伪:不退回文本核对,不采纳客户端自报链字段

## B. 合盘重算 403 不回落旧快照

**问题**:无 contextToken 的合盘快照落穿 API 重算;若 A/B 盘本身也是老快照,重算 403。reviewer 主张:升级前能正常显示评估卡的合盘,升级后整对失败——应回落旧快照显示。

**决策**:维持不回落(4xx 显式失败;仅离线/超时回落)。

**我方理由**:
1. 2026-10-07 已拍板"4xx/5xx 回落旧标签 = 拿旧值掩盖失败,违反错误显式传播"(CLAUDE.md 全局约束),同轮实现了离线回落、4xx 不回落。
2. 403 的语义是"该重算了",不是"暂时不可用"。回落旧快照 = 旧引擎规则标签(合冲判定序变更前的刑害点名)与新规则重算的评估卡同屏自相矛盾——这正是引擎规则×prompt 版本联动守护栏(CLAUDE.md)要防的错配,对"专业不忽悠"定位的伤害大于短期显示失败。
3. 恢复路径完整:重新排盘 → 新 token → 重算落新快照。本轮 d1aab16 已把「重新排盘」按钮接到凭证失效出口,用户有明确操作路径。

**反方最强论点**:用户视角是"升级把能用的东西弄坏了"——老用户没有任何过错,却要重新录入出生信息才能看回原本就有的内容;而回落旧标签的伤害(标签可能过时)是间接的、概率性的。

**我方回应**:这是"数据迁移缺过渡期"的体验成本,第九轮拍板"旧盘 403 无自动迁移(重新排盘恢复)"时已知并接受;自动迁移的替代方案(自动重排)见 G 条,受快照字段限制不可行。

**证据**:`CompatibilityViewModel.computePair`(回落判定 `isOfflineOrTimeout` 单一事实源);CLAUDE.md「错误显式传播」与「引擎规则版本×合盘 prompt 版本联动守护栏」。

## C. 付款取消在飞免费链:本地退次数、服务端不退,两本账不对齐

**问题**:购买完成 → 付费生成取代在飞免费链(cancel)→ 客户端把本地那次免费次数退回,但服务端配额已扣(LLM 已在烧)。reviewer 主张"次数对不上"。

**决策**:维持现状。

**我方理由**:两本账语义不同,不是同一本账的两份抄写——
- 本地池(10/日):**体验配额**,按"用户是否拿到结果"结算。免费生成被付费链取代,用户没拿到免费结果且非其过错,退回正确。
- 服务端池(30/日,按 user_id/IP):**成本护栏**,按"是否真烧 LLM"结算。那 1 次 LLM 调用是真实成本,退了会打开"打断即免单"的刷法。

跨账本强行对齐(本地也扣/服务端也退)各自都会引入对方的问题:本地不退 = 用户无过错损失体验额度;服务端退 = 免费烧 LLM 通道。

**反方最强论点**:两本账数值独立漂移,极端情况下用户 App 显示剩余 10 次、服务端已 429,用户无法理解差异;共享 IP 用户更是两头挤压。

**我方回应**:漂移方向是"服务端先紧"(30 次含翻译计数,正常单用户达不到);429 已映射达限态含倒计时(b3c76d8),不再是无解释的通用失败。真正的结构性缓解要靠 D 条(退款口径)与匿名维度拍板,而非在取消路径上对账。

**证据**:`InterpretQuotaLedger`(本地账本,`refundOnFailure` 关账防双退);`interpret.py` 配额 factory(leader 扣款取舍注释)。

## E. 翻译链 403 不接 contextTokenExpired 特判

**问题**:本轮把凭证失效落成结构化 `.contextTokenExpired` 态(生成路径三模块全覆盖),但**翻译链**的 403 仍走既有降级:保留原文显示 + 章首小注「翻译失败 · 重试」手动重试——老盘翻译 403 时该重试必再 403。

**决策**:本轮不动,列下轮候选。**〔2026-10-08 晚更新:已按下述「低成本正确修法」落地——深度解析与合盘的翻译链 catch 均接 `isContextTokenError`,原文保留 + 提示条改「重新排盘」指引(`TranslateHintBar.Mode.tokenExpired`,不渲染重试按钮),不入 `translationFailedModules`(章首小注即不渲染死循环重试),断链防后续章白烧;回归锚 `TranslationFlowTests.test翻译链凭证失效_原文保留_提示条走重新排盘指引`。〕**

**我方理由**:翻译失败与生成失败的降级语义不同——生成失败只剩错误文案,翻译失败**原文保留显示**(内容不丢,用户仍有可读内容);接特判需牵动 `translationFailedModules` / `autoTranslationOutcomes` / 提示条分诊的既有语义(09-02~10-06 多轮收敛的结果),本轮改动风险大于收益。

**反方最强论点**:重试按钮对老盘是死循环入口,与"生成路径有出口、翻译路径没有"不一致。

**我方回应**:成立。缓解因素:老盘翻译 403 场景 = 升级前存档 + 切语言,重排盘后自愈;但"重试再 403"确实无解释。下轮把翻译链 catch 也接 `isContextTokenError`(原文保留 + 提示条改指引文案,不引入新态)是低成本正确修法。

## G. 自动静默重排重签不可行(为什么出口是按钮不是自动)

**问题**:三轮 review 建议凭证失效时"自动用已存出生信息静默重新排盘拿新 token 再重试"。

**决策**:不可行,出口为「重新排盘」按钮(post `.switchTab` 到深度解析 tab)。

**我方理由**:重新排盘需要完整排盘入参,而 `ChartSnapshot` 持久化字段只有 `birthSolarTime`(真太阳时,排盘**产物**)、gender、经纬度、时区、ziHourRule——**缺 hourKnown / lateNight / 钟面 birth_datetime / geonameId**。真太阳时含经度修正,逆推钟面时间在 DST 边界/时辰未知盘上不可靠;hourKnown 丢失意味着时辰未知盘重排会按已知时辰算,**换盘**而非重签。用不可靠参数静默重排 = 同一用户出现 contentHash 不同的两张盘,破坏内容寻址与缓存/购买绑定。

**反方最强论点**:让用户"自己去别处重新录入"是产品失败;至少可以在快照里补存排盘入参,让未来版本能自动重签。

**我方回应**:补字段属 schema 演化(可做,ChartSnapshot 有 payload JSON 通道),但涉及排盘请求重建链路与迁移,不是本轮"修 bug"的边界;同意作为独立议题立项。
