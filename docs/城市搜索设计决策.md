# 全球城市搜索 + 出生地时区改造设计决策

Generated on 2026-08-15(grill-me 会话锁定)
Status: ACCEPTED(待实施)
关联文档: `bazi-app-design-doc.md` / `docs/合盘多选设计决策.md` / `CLAUDE.md`(红线:确定性 / 客户端不做历法计算 / 错误显式传播 / 不擅自加依赖)

## 背景(现状审计结论)

现状「出生地」实现 = **52 城硬编码,两处维护**:

- iOS `CityList.cities`(BirthFormView.swift:186-199):40 中国城市 + 12 海外城市,纯中文字符串
- 后端 `CITY_LONGITUDE`(city_longitude.py:10-66):仅存经度(2 位小数),**无纬度、无时区、无省份/国家**
- 交互:原生 `Picker` 滚轮精确匹配,零搜索、零拼音、零别名(BirthFormView.swift:69-75;合盘快速添加复制了一份 CompatibilityConfigView.swift:267-269)

审计发现的**关键事实**:

1. iOS 用 `JSONEncoder .iso8601` 发送(APIClient.swift:28-31),日期被转成 UTC "Z",设备时区信息在传输中丢失
2. 但后端 `timezone_central_longitude` 从 offset 推算时区中心经度(true_solar_time.py:37-42),UTC 化减掉的时数与 tz_central 归零**数学上恰好抵消** → 真太阳时 = UTC + 经度×4分 + EoT,与时区表示无关 → **国内盘结果是对的**
3. **真正的 bug**:DatePicker 按**设备当前时区**解释用户输入的钟面时间。出生在海外、人在国内录入的用户(现状 12 个海外城市每一个),时辰错 15+ 小时;「手动输入经度」开关救不了(只改经度,不改钟面解释)

因此本改造必须**城市搜索与时区语义一起修**,否则只是把错误面从 12 城扩大到全球。

## Q1 范围:全修(用户确认 A)

城市数据库自带 IANA 时区,顺手修掉「设备时区 ≠ 出生地时区」的静默错误。选择在 pre-launch(未上 TestFlight)窗口做:改 API 契约零迁移成本,上线后再改是迁移地狱。

- 包含:夏令时按 IANA tzdb 历史规则自动套用(1986-91 中国夏令时、1940s 伦敦双夏令时、美国 2007 前 DST 日期)
- 不做:1949 前 LMT(地方平太阳时)边角的显式 UI 提示(tzdb 本身有记录,自动生效,不额外提示)

## Q2 数据源:GeoNames 离线 SQLite(用户确认 + pypinyin 已批准)

```
tools/build_city_db.py
  入口: GeoNames cities dump(cities1000/5000,见 Q9 体积门槛)
        + alternatenames 预提取(zh / zh-Hant / en)
        + admin1Codes(CLC 码)
        + CLDR territory 表(~250 国中文名)
        + curated_aliases.tsv(人工精选别名,进 git)
  出口: ios bundle 的 cities.sqlite
        + manifest.json(条目数 / 数据集版本 / GeoNames dump 日期 / 内容 hash)
  GeoNames 原始 dump 不进 git(几十 MB),脚本按需下载,幂等可重跑
```

选型否决记录:

- **Apple MKLocalSearchCompleter**:结果随地区/版本漂移(违反确定性)、必须联网、中国数据 GCJ-02 坐标系(经度系统性偏移)、时区需二次查询
- **高德/百度 POI**:仅中国、key+配额、GCJ-02
- **混合(离线+长尾在线)**:复杂度翻倍,出生地场景几乎碰不到极冷门在线兜底收益

其他要点:

- **不用 FTS**(iOS 系统 SQLite 不带 FTS5),用 keys 表 + 归一化后 LIKE,200ms 防抖
- 许可 **CC-BY 4.0**:关于页加 geonames.org attribution 一行
- `pypinyin` 仅构建期(从汉字生成全拼+首字母,补 GeoNames `ascii_name` 拼音覆盖不全),**非运行时依赖**,已按「不擅自加依赖」规则报备获批
- 后端零城市表(Q4),同步只剩 iOS 一边

## Q3 粒度:市/县级(用户确认 A + 海外全量)

- 中国:直辖市 + 地级市 + 县级市(昆山、义乌都在 `cities1000`);海外:城市级(Berkeley、Cambridge 靠「州/省 + 国家」消歧)
- **不做市辖区单列**(海淀、浦东不独立成条):市内经度差 ≤0.5° → 太阳时差 ≤2 分钟,对 2 小时一个的时辰桶零影响;条目省 30%,避开「北京/北京海淀」重复匹配排序坑
- 「海淀」输入靠**区县别名**(海淀→北京)兜住:只进搜索索引,不进主表;重点城市人工维护(长辈录入场景:量不大但存在)
- 长尾精度需求由 Q8「自定义地点」承接

## Q4 API 契约:客户端发物理真值,后端删表(用户确认 A)

新请求字段(排盘 / 合盘现排 B 同契约):

```
birth_datetime: "1988-05-05T02:30:00"   # 裸钟面时间(无 offset),语义见 Q5
timezone: "Asia/Shanghai"                # IANA 时区名(必填,后端校验合法性)
longitude: 116.41                        # 物理真值,客户端来自 SQLite / 手动输入
latitude: 39.9042                        # 存档用(下游真太阳时不用纬度)
place_name: "北京"                        # 展示用
geoname_id: 1816670                      # 仅日志/诊断,非 load-bearing
```

- 后端**删除** `CITY_LONGITUDE` + `resolve_longitude()`(city_longitude.py),只做范围校验(经度 ∈[-180,180],tz 合法 IANA 名)
- 理由:城市数据不比「手动经度」更特权(现状本就客户端直传);消灭「App 内置 DB v3 vs 后端表 v2」版本漂移(三边一致性教训)
- `content_hash` 改为基于**归一化物理量**(UTC 时刻 + 经度固定精度 + 时区 + 性别 + zi_hour_rule):城市表示从「北京」变 116.41 不该换 hash;老开发期缓存/快照全失效,pre-launch 可接受
- `ChartSnapshot` 增 `cityTimezone` / `cityName`(展示)/ 纬度字段
- 同步契约 `city_longitude` 字段随引擎响应同步调整

否决:后端按 `geoname_id` 查同源种子表(引入 App↔后端 DB 版本漂移,收益仅「防客户端乱填」——非威胁模型);保留 `city: String` 后端表扩列(字符串精确匹配脆弱性原样保留,重名城无法区分)。

## Q5 时区解释:后端 zoneinfo(用户确认 B)

「客户端不做历法计算」红线的边界判定——时区解释本质是历法换算,归后端:

- iOS 发**裸钟面时间 + IANA 时区名**;后端 stdlib `zoneinfo`(Python 3.9+,**非新库**)套历史规则转绝对时刻
- 历史规则全进 pytest(对盘文化同构):1986-91 中国夏令时边界、伦敦 BST/BDST、美国 2007 前 DST
- **歧义策略显式化(错误显式传播)**:
  - 秋令时回拨的重复小时 → 取早的(`fold=0`)
  - 春令时跳过的不存在小时 → 按偏移平移
  - 两种情况 + 夏令时期切换点附近 → 降级到既有 `boundary_warning` 通道提示「时间处于时制切换附近,请核对」,不静默吞
- 用户记忆的钟面时间(含夏令时期)= tzdb 记录的实际墙钟,不需要问「你这是夏令时吗」
- iOS 端 DatePicker 挂出生城市时区的 Calendar 保 WYSIWYG(显示 10:00 就是当地 10:00),**换算责任不落客户端**
- `.iso8601` 编码策略随之移除裸时间序列化(APIClient 需自定义 formatter 或发字符串)
- 部署注意:后端若将来容器化(Alpine)需系统装 `tzdata`;当前 macOS/Linux 开发环境自带,零动作
- 真太阳时公式本身不动(tz-invariant,已验证数学抵消)

## Q6 搜索匹配:全形态,不做纠错(用户确认「全要」)

**输入形态覆盖(构建期全部进索引)**:

| 用户输入 | 命中 |
|---|---|
| 简体前缀/包含:`乌木` | 乌鲁木齐 |
| 繁体:`臺北` `倫敦` | 台北 / 伦敦 |
| 全拼:`wulumuqi` `xian` | 乌鲁木齐 / 西安 |
| 拼音首字母:`wlmq` | 乌鲁木齐 |
| 英文:`Cambridge` | 剑桥(英/美多结果靠副标题消歧) |
| 别名:`三藩市` `海淀` | 旧金山 / 北京(「帝都」类网络别称**不进**) |

**归一化**:大小写折叠 + 变音符折叠(ü→u、é→e:`munchen` 命中 München,`san jose` 命中 San José)+ Unicode NFC。

**v1 不做错别字/混拼纠错**(编辑距离、n/l、zh/z、前后鼻音):大坑且与确定性文化相性差;联想场景用户打半截字(`乌木`)结果已出,实际伤害小。Backlog 留「常见混拼容错」。

**排序公式**:`匹配质量(前缀>包含) > 人口 > 输入脚本加权 > 最近选择`

- 输入是汉字/拼音 → 中国城市优先;英文 → 中英平等竞争(英文输入者可能就是在搜海外)
- 同名消歧靠结果行副标题,**不**做「先选国家再搜」两步交互
- 空输入态:最近选择 + 热门城市网格(旧 52 城即种子)

性能:14 万城 × 3-4 key ≈ 50 万行 SQLite LIKE,iPhone 上 200ms 防抖流畅,无需 FTS。

## Q7 命名与显示(用户确认)

- SQLite 每城存 `name_zh` / `name_en` 双列:中文 UI 中文优先(旧金山、伦敦、雪梨),**无通行中文名的小城市不强行音译**,fallback 本地名(Corvallis、Schenectady);英文 UI 取 `name_en`(中国城市即 Beijing)
- 人工精选别名表(几百条以内,`curated_aliases.tsv` 进 git,构建期合并):三藩市、雪梨、纽瓦克等 GeoNames 缺的华人口语名
- 副标题:国家中文用 **CLDR territory 表**;`admin1`(州/省)中文 GeoNames 覆盖不全,**能提多少提多少,英文兜底**——v1 不为「俄勒冈还是奥勒冈」做专项工程
- 结果行(中文 UI):

```
旧金山        San Francisco · 加利福尼亚, 美国
Corvallis     Oregon, 美国
西安          陕西, 中国
```

## Q8 交互与「自定义地点」(用户确认)

**交互形态**:

- 出生地卡片放假搜索框(显示当前选中「北京, 中国」或占位),点击推 **sheet**:搜索框自动聚焦 → 空态「最近选择 + 热门网格」→ 键入即出列表 → 点选回填收起
- 回显**只显示**「城市, 国家」;经度/时区不显示(噪音),收进结果页 `calc_rule_snapshot` 展示位
- 用 sheet 不用内嵌:键盘+长列表要全屏空间;三入口无脑复用

**砍「北京」默认值**:`selectedCity = "北京"`(DeepAnalysisViewModel.swift:62)意味着用户忘选就静默生成错误命盘。改**无默认 + 必选校验**(内联错误通道现成),空态占位「搜索出生城市」;热门网格把点选成本压到一次点击。

**不加 GPS**:出生场景 GPS 几乎无用(出生≠现在在原地),代价是 CoreLocation 权限弹窗 + 隐私清单 + 「定位的是现在不是出生地」心智误导。

**「手动输入经度」升级为「自定义地点」高级模式**:

- 现状开关只填经度、钟面仍按设备时区解释 → Q1 要修的 bug 在此路径原样保留
- 升级为:折叠的「高级」入口,展开后 = **经度 + IANA 时区必填**;时区给常用列表(~40 条带样例:「GMT+8 · 中国标准时间」)+ `Etc/GMT-X` 固定偏移兜底「我知道当年就是 UTC+9」——全是合法 IANA 名,后端 zoneinfo 统一解释
- 存在理由:村、GeoNames 漏条、出生在医院基地/船上等长尾的诚实出路;砍掉会逼用户编错误城市

**精度**:经纬度存 GeoNames 原生 4 位小数(约 10m 级,对应太阳时 2 秒,远超需求);传输不四舍五入;`content_hash` 归一化到固定精度字符串保证确定性。

## Q9 落地:vertical slice + 守护栏(用户确认)

**入口统一**:城市输入现存 3 处——深度解析 `BirthFormView`、合盘快速添加(CompatibilityConfigView.swift:267)、onboarding 表单(BirthInfoConfirmSheet.swift:36 回显)。全部换共享组件 `CityPickerField` + `CitySearchSheet`;`CityList` enum 删除;搜索 UI 文案进 `Localizable.xcstrings`(v1 中英)。

**实施顺序(每片独立验收,随时可停)**:

1. **S1 构建管线**:`build_city_db.py` + cities.sqlite + manifest.json + spot check;**验收含实测体积** —— ≤25MB 用 `cities1000`(安装后约 20-25MB / 下载增量约 10MB),超了或嫌大切 `cities5000`(约 10-12MB;只丢 1-5 千人口小镇直接命中,县城/行政中心照常在,经度差 ≤0.3° 对时辰零影响)。同一管线同一 schema,一个参数切换,可逆
2. **S2 后端契约**:删 `CITY_LONGITUDE`/`resolve_longitude`、`birth_datetime` 改裸钟面 + `timezone`、`zoneinfo` 解释、DST 歧义用例、现有 30 用例对盘保持绿;合盘「现排 B」同契约顺带改
3. **S3 iOS 组件**:`CityPickerField`/`CitySearchSheet` + 三入口替换 + 砍默认值 + 必选校验
4. **S4 自定义地点高级模式**(经度 + 时区必填)
5. **S5 golden queries + 全量回归**:「输入→期望首位命中」表(JSON 进 repo)作为搜索质量单一事实源,Swift XCTest 读同一份跑断言

**守护栏(学 prompt 三边一致性教训)**:

- `tools/check_city_db.py`:SQLite 结构 + manifest hash 一致 + 关键城市抽查(北京 116.4/Asia/Shanghai、洛杉矶、伦敦、悉尼经度时区)——**动了 build 脚本或 sqlite 必须跑且 PASS**
- backend pytest 新增:zoneinfo 历史规则(1986-91 夏令时边界)、fold 策略、tz 校验

## 红线遵守情况

| 红线 | 遵守方式 |
|---|---|
| 不擅自加依赖 | 运行时**零**新库(zoneinfo 是 stdlib);pypinyin 仅构建期且已获批 |
| 错误显式传播 | DST 歧义/不存在小时不静默吞,全部降级 `boundary_warning`;tz 非法/经度越界显式报错 |
| 确定性 | 单一事实源构建脚本 + manifest hash + golden queries 共享 JSON;搜索纯本地纯函数 |
| 客户端不做历法计算 | 时区解释归后端 zoneinfo(Q5) |

## 不做(本次范围外)

- 错别字 / 常见混拼纠错 —— backlog
- 市辖区独立条目(海淀、浦东单列)
- GPS 定位入口
- 「先选国家再搜」两步交互
- admin1 中文名专项工程 —— 英文兜底
- 1949 前 LMT 显式 UI 提示 —— tzdb 自动生效
- 在线搜索兜底(混合方案)
- FTS5 —— iOS 系统 SQLite 不带,LIKE + 防抖足够
