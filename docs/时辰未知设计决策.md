## 背景

排盘准确性是产品命根。当前 onboarding 出生表单(`BirthFormView`)存在两个同源的数据质量洞:

1. **无「时辰未知」入口**:不知道出生时刻的用户,表单里只有躺着的默认时刻,没有任何显式承认「我不知道」的路径。用户只能(a)不碰表单用默认值,或(b)用「时辰快捷选」挑一个貌似接近的——两种都以**无痕迹的假精度**建档,后端永远收到一个看起来精确的 `HH:mm:ss`。
2. **默认日期洞**:`DeepAnalysisViewModel.birthDate` 默认 1990-03-15,校验只有「不晚于当下 + 选了城市」两条(`DeepAnalysisViewModel.swift:152`),日期字段可以完全不触碰就提交,现在只靠二次确认 sheet 兜底。

### 时柱依赖清单(backend 实测,决定一切后续设计)

| 依赖级别 | 内容 | 代码位置 |
|---|---|---|

| **不依赖(节气交界日除外,见下)** | 生肖(年支) / 年月日柱 / 大运干支序列 / 流日流年 | `bazi_engine.py:94` / `luck.py:10` |
| **节气边界依赖** | 立春日 → 年柱 + **生肖**;节交界日(12 节/年 ≈ 3.3% 用户)→ 月柱 → 调候(查月支) + 得令(扶抑最大权重 `DELING_WEIGHT=5`) + 大运干支序列 | `current.py:20` `getYearInGanZhiByLiChun()`;`bazi_engine.py:87`(lunar_python 节气表精确到分);回归佐证 `tests/test_bazi_calculate.py:128` |
| **弱依赖** | 大运**起运年龄**:由到节气的时间差换算(3天=1年 → 1 时辰≈5天),时辰未知 → `start_age`/`start_year` 漂移 ±2-3 个月,边界差 1 年 | `luck.py:22` `ec.getYun()` |
| **边界歧义** | setSect(1) 23:00 换日 → 深夜出生者连日柱都有歧义窗。**注意换日判定发生在真太阳时上,不是墙钟**:偏移 = EoT + (经度−时区中心)×4min,喀什 offset ≈ −176 分钟 → 墙钟歧义窗实际是次日 01:56-02:56 | `bazi_engine.py:80-88` / `true_solar_time.py:69` |
| **契约** | content_hash 含 2 小时时辰桶 | `content_hash.py:27` |

**关键级联**:喜忌是深度解析/合盘/每日运势三大 AI 模块 prompt 上下文的根基。没时辰 ≠ 少展示一柱,而是三大模块失去核心依据。

**同样关键的反向事实**:**日主(日干)在缺时辰时是完整的**。日主是产品的锚(`anchor_sentence` 即日主句,深度解析 Tab 顶部 instant 显示)。缺一柱是缺 25%,不是缺 100%——本文档所有降级设计建立在这个事实上,而不是「没时辰≈什么都没有」。

## D1 单一入口,系统分流

表单加显式「不知道出生时刻」选项(checkbox 或 chip)。选中后时刻输入收起,系统统一进入降级流程。

否决「用户自选两条路」(不知道时辰后让用户选「猜个大概」或「接受不准看三柱」):

- 用户不该被问「你要哪种质量的数据」这种元问题——数据质量责任在产品,不在用户
- 与「专业不忽悠」一致:产品替用户做诚实选择

否决「两步串联」(先问时段,给了走模糊时柱,没给降级):时段给出的仍是 2-3 个候选时辰,后续处理复杂且引向 D2 已砍掉的反推。

## D2 砍掉人格题反推(用户原始方案一的部件)

用户最初设想:选完时段后「问几个个性问题,看哪个(时辰)符合他,按这个来」。**砍掉**,理由:

1. 用性格问卷「算出」出生时辰是典型算命软件套路,与 Memorable Thing「专业不忽悠」直接冲突
2. 猜错时柱 → 喜忌错 → 三大模块全错,**且用户不知道是猜的**——错误代价被完全隐藏
3. 反推映射表本身无从验证,违背「确定性判断不交给玄学」的 LLM 边界原则

「问几个问题看个性」若未来要做,只能作为生肖屏/Profile 的娱乐内容(类似星座趣味),永不参与排盘。

## D3 只问一个二值问题:是否半夜出生

「不知道出生时刻」后问一句:**「你是否在半夜(约 11 点之后)出生?」**(是 / 否 / 不确定)

### 为什么不是四段时段(原方案已否决)

原方案收集「上午 / 下午 / 傍晚 / 深夜」四段。**砍掉**,理由:

1. **对多数用户是个没有作用的问题**。v1 里时段唯一的计算用途是判断深夜日柱歧义。选「上午」的用户,这个问题什么都没做——但用户会以为它被用上了(「我说了上午,所以算的是上午的盘」)。这是一种**隐性假精度**,与 D1 要消除的东西同构
2. **四段边界无法定义干净**。凌晨 0-5 点归「深夜」还是「上午」?判据字段必须有唯一定义,否则 iOS 采集 / 后端判定 / payload 存档三边各写各的
3. 二值问题问的正是唯一需要的那 1 bit,诚实且用途对用户可见

### v1 用途(唯一)

**日柱歧义判断**。判据是一个统一的区间测试,**不是**「答否即确定」这种单边规则(2026-09-01 review 修正,原写法在东偏经度漏报、西偏经度过度降级):

1. 由二值答案取墙钟候选区间:**否** → `[00:00, 23:00)`;**是** → `[23:00, 24:00)`;**不确定** → 全天 `[00:00, 24:00)`
2. 整个区间加真太阳时 `offset_minutes`,得到真太阳时候选区间
3. **该区间内是否包含一个真太阳时 23:00 换日点** —— 包含则日柱歧义(标未知,走 D5 全拦截分支),不含则日柱确定

判定窗口**不写死 23:00-24:00**,offset 由出生地经度 + EoT 决定(`true_solar_time.py:69`)。

为什么必须是区间测试而不是阈值规则(实测,offset = 真太阳时 − 墙钟,单位分钟):

| 场景 | offset | 答案 | 精确结论 | 单边规则会给出 |
|---|---:|---|---|---|
| 喀什 75.98°E | −176 | 是 | **确定**(真太阳时 20:04-21:04,同日) | 误判歧义 → 该用户被 D5 全拦,**过度降级** |
| 成都 104.1°E | −63 | 是 | **确定** | 误判歧义,过度降级 |
| 上海 121.5°E | +6 | 否 | **歧义**(22:54-23:00 墙钟落次日) | 误判确定 → **静默给错日柱** |
| 抚远 134.3°E | +57 | 否 | **歧义**(22:00-23:00 落次日) | 误判确定,静默给错 |

「不确定」恒歧义(任何 24h 区间必含且仅含一个 23:00 点),由该测试自然得出,不需另写规则。

### 存档元数据

ChartSnapshot payload 存 `late_night`(bool?),供未来「候选时辰共识盘」——本期不做。

明确不做:不用它反推具体时辰、不用它取中点假装时柱。

## D4 喜忌引擎:输出「不可用」,复用从格先例

时辰未知时后端喜忌引擎(扶抑+调候+从格)**不硬算**:

- `day_master_strength="unknown_hour"`,favorable/unfavorable 留空
- LLM 拿到该状态后诚实告知「时辰未知,喜忌分析需要准确时辰」

这与架构里已有的从格检测 D3 先例完全同构(命中 → `special_pattern` → 喜忌留空 → LLM 诚实降级,`xiji.py:240-243`),零新范式。

否决「引擎改支持 6 字计算」(分母 8→6):权重公式按 8 字校准,改分母后数值意义变了;从格 6/8 阈值缩到 6 字后误判率未知;喜忌是三模块根基,可靠性无法验证。

否决「排盘直接拒绝无时辰请求」:连生肖/三柱/大运这些可靠结果也一并拒绝,与「能给的诚实给」相悖。

附:神煞按三柱查(时支神煞自然缺失),输出标注「可能不全」;大运干支序列、生肖、流日流年照常(起运年龄按依赖表标注误差)。

## D5 内容策略:按章节切,不按模块切

### 为什么不是模块级 all-or-nothing

产品本身是**章节粒度**切免费/付费的(深度解析 10 章 = 2 免费 + 8 付费,`MONETIZATION.md` §免费/付费内容分界),时辰缺失的影响也是按章节分布的。用模块粒度去切章节粒度的问题,会同时切多了和切少了。

原方案「深度解析整模块拦截」的致命后果:模块入口后面就是 2 章免费真 AI 内容,在入口拦等于**把免费内容一起拦掉**,直接违反 `MONETIZATION.md` §设计哲学 第一条「免费章节也是真 AI 内容(不是占位/缩水版),用户买之前能感知 AI 真有料」。后果链:无时辰用户看不到任何 AI 内容 → 没有「这 AI 真有料」体感 → **补时辰动机为零** → 拦截页变成死胡同。

### 10 章按「依据在不在」分三类

| 类别 | 章节 | 说明 |
|---|---|---|
| **三柱足够** | 命盘(三柱十神总览) / 日元的「日主心性」半章 / 婚姻感情的配偶宫部分 | 配偶宫在**日支**不是时支;内容真实,只缺一柱 |
| **降级可讲** | 性格底色 / 事业方向 / 事业与财富的大运部分 | 换轴叙事:以日主为主轴,不谈喜忌 |
| **必须时辰** | 五行(喜忌+调候) / 格局倾向 / 身体健康(调候) / 日元旺衰 / 子女缘 | 引擎明确不可用,讲了就是编 |

### 结论

| 内容 | 定位 | 无时辰策略 |
|---|---|---|
| 每日运势 | 免费(B2 入口) | **降级提供**:走「日柱×流日十神关系」叙事,明示局限 |
| 每日运势(日柱亦歧义时) | 免费 | **全拦截**——没有日主就没有任何依据,见下 |
| 深度解析 免费 2 章 | 免费预览 | **照给**,降级叙事(日主为轴,不谈喜忌) |
| 深度解析 付费 8 章 | 付费 | **全拦**,即使其中 3 章「三柱足够」 |
| 合盘 | 半免费同形态 | **任一方无时辰 → 整对拦,免费部分也拦**(见下「合盘为何免费也拦」);双方有时辰的对完全不受影响(复用 D13 对级隔离) |

### 合盘为何免费也拦(2026-09-01 review 修正)

本决策最初写「合盘免费部分照给、付费部分拦」,与深度解析同形态。**该写法不成立**:`_COMPATIBILITY_REQUIRED_FIELDS` 被 `compatibility` / `compatibility_free` / `compatibility_paid` **共用同一份**(`prompts.py:643` 注释明写「共享 header」),其中含 `hour_a` / `hour_b` / `day_master_strength_a` / `favorable_a` 等时柱依赖字段——免费章与付费章用同一套上下文,免费章物理上渲染不出来。

因此合盘的正确形态是**整对拦**:任一方(自己或对方)无时辰 → 该对不可发起。这不是产品选择,是契约事实。若未来要做「合盘免费降级」,需要单独一份 `compatibility_free` 字段集,属独立课题。

**付费 8 章全拦(含「三柱足够」的 3 章)的理由不是内容质量,是定价承诺**:$17.99 对应「深度、定制、不水」,卖 8 章里的 3 章半,用户感受是被削了价值,不是被诚实对待。**明确写死:不做按章节的部分售卖。**

### 日柱亦歧义的用户(D3 答「是」/「不确定」)

这批人没有日主,`daily_fortune` 的 REQUIRED_FIELDS 里 `day_master` / `day_master_element` / `day_pillar` / `day_stem` / `day_relation` 全塌(`prompts.py:664-673`),免费降级不成立 → **每日运势也拦**,直接引导补时辰。D3 的二值问题正是为了把这批人尽量缩小(答「否」的用户日柱完全确定)。

代价(二期实施):每日运势 prompt 要支持喜忌缺失分支 → `REQUIRED_FIELDS` 三边同步 + evalkit 跑一轮(CLAUDE.md 双护栏)。

## D6 付费边界:拦在付费墙,不拦模块入口

### 主论证:双重收费(不是退款风险)

entitlement 是**消耗型 IAP,严格按 `content_hash` 绑定**(`MONETIZATION.md` §决策汇总,用户原话「修改生辰要重新购买」)。所以无时辰用户一旦能买,必然序列是:

> 无时辰买 $17.99 → 后来补上时辰 → content_hash 变 → 系统要求再付 $17.99

**同一个人、同一张盘、收两次钱。这是现有付费模型下的必然结果,不是概率性风险。** 「先付钱→发现没内容→退款+差评」只是次要论证。

### 拦截点

```
深度解析入口     → 放行
2 章免费内容     → 给(日主为轴,不谈喜忌)
第 3 章付费墙    → 拦:不显示价格、不显示购买按钮,
                   改「补充出生时刻后解锁」+ CTA(直跳 D7 入口)
合盘同形态
```

三件事同时成立:免费内容照给(与付费哲学一致)/ 钱一分不收(避开双重收费)/ **拦截发生在用户刚被免费内容说服的那一刻**——转化率最高的位置。

否决「拦在模块入口(早于付费墙)」:那是对方向的过度修正。要避免的是**看到价格并付款**,不是**看到内容**。

### App Store 促销码边界

`/api/entitlement/redeem` 是 **StoreKit2 购买完成后同步后端 + Apple 校验**的端点(`backend/app/models/entitlement.py` docstring;`PurchaseManager.swift:203`),不是兑换码入口。仓库内无任何兑换码实现;`MONETIZATION.md:272` 写「礼物卡/赠送 — v2」、`:273` 写「苹果促销代码 v1 不主动发」,且苹果 offer code 在 App Store 内兑换,App 侧无拦截点。

因此**没有「拦不拦 redeem」这个决策**。真实边界只有一条:用户经 App Store 促销码拿到 entitlement 后进 App 仍无时辰 → 权益记账正常、内容仍按上面的付费墙拦,落到同一个补时辰引导页。

## D7 补时辰:三个有上下文的触点

### 为什么不是「Profile 常驻入口」

Profile 是仓库不是钩子——没人会主动去 Profile 补一个自己都没意识到缺了的字段。

**根因:没时辰的用户不知道自己损失了什么,所以没有补的动机。动机必须在用户正在看内容的时刻制造出来,不是在一个空拦截页里。**

### 三触点(按「有上下文」排序)

1. **命盘表格的时柱列(最强,近零成本)**:`PillarsTable.swift:19` 那一列画成留白 + dashed hairline(DESIGN.md 里 dashed 已是锁定/临时态语义,现成),点击进补时辰。**四柱少一柱在视觉上不言自明**,比任何文案有说服力;「留白」贴合水墨美学,不是错误提示
2. **每日运势末尾(最高频)**:唯一每天触达无时辰用户的免费模块。一行静默文字,**不是弹窗**:「这份运势只用了你的日柱。补上时辰可以看到时辰运势与喜忌。」
3. **付费墙 CTA(最低频,转化最高)**:见 D6

**明确不放:onboarding 生肖反馈屏(US-ON-01)**——那是产品第一个「哇」时刻,在那里说「你的数据不全」是自毁开场。

### 补时辰入口本身

只补时辰一个字段(不重填姓名/性别/地点)。现状「只能重置命盘重走全部表单」保留给改日期/性别/地点场景(对齐生肖决策 Q20)。
入口也要能作用于**合盘 roster 里的他人命盘**,不只是命主自己。

### 永久无时辰用户(新增)

八十年代前出生 / 被收养的用户,时辰是**真的补不上**。对他们,常驻入口 + 每次付费墙拦截 = 持续的失败提示。

需要一个「**我确实不知道**」确认态:勾选后提醒降级为静默(入口保留在 Profile,但三触点不再主动提示)。这是「专业不忽悠」的另一面——不忽悠也包括不假装问题能解决。

### content_hash 与 entitlement

补后 content_hash 变(2h 时辰桶参与计算)→ 视为新命盘,老三柱盘归档保留,缓存按新 hash 自然重建。

**entitlement 重绑是独立课题,本决策范围内不做**:`entitlement.py:87-94` 在 transaction_id 幂等命中且 content_hash 不同时直接 `mismatch_reject` 抛错,现有代码**主动拒绝**重绑——这是实打实的新工作量,不是「内容寻址的红利」。且该坑今天已存在(重置命盘改日期/地点 → 已购权益搁浅),非本决策引入。因 D6 已拦购买,无时辰用户不存在待迁移权益。

## D8 默认日期洞一起修

出生日期改「未选择」初始态,必须触碰 DatePicker 选过才能提交;配合时辰未知 flag,表单状态机一次改到位。`birthDate` 变 Optional,绑定/二次确认 sheet/测试链路同步小改。

### 把矛盾变成教育

「日期必须填」与「时刻可以不填」并列,用户会问为什么。这是「专业不忽悠」的表达位——表单上直接写明:

> 日期决定年月柱与生肖;时刻决定时柱与喜忌。不知道时刻可以先跳过。

### 工作量备注(不要低估)

现状日期与时刻是**同一个** DatePicker(`BirthFormView.swift:110-119`,`displayedComponents: [.date, .hourAndMinute]`)、同一个 `birthDate: Date` 绑定,**无法只隐藏小时分量** → 必须拆成两个 picker、两个绑定。

Optional 化波及:`OnboardingView.swift:110`(生肖屏取 birthYear)/ `BirthInfoConfirmSheet.swift:92` / `DeepAnalysisViewModel.swift:60,154,176,189-199` / `APIClient.swift:387` mock 路径。

## D10 节气边界:双排盘比对

无时辰时,年/月柱在节气交界日**并非确定**(见依赖表)。检测方式:

对该出生日的 00:00 与 23:59 各排一次盘,比对**年柱与月柱**——不一致的柱标未知。

**日柱不走这对探针**(2026-09-01 review 修正):setSect(1) 下墙钟 23:59 的真太阳时几乎必落进 `[23:00,24:00)` 换日窗 → 探针恒返回次日日柱,字面实现会把**所有**无时辰用户的日柱判为歧义,与 D3、与「三柱盘」前提直接冲突。日柱一律走 D3 的区间测试(那个判据已经把节气与换日两件事分开处理:节气影响年月柱,换日影响日柱,互不交叉)。

命中后果:

- 月柱歧义 → 调候(查月支)+ 得令(`DELING_WEIGHT=5`)+ 大运干支序列 一并不可用
- 年柱歧义(立春日)→ **生肖亦不可用**,onboarding 生肖屏走降级(告知需要时辰才能确定属相,给补时辰入口),**不猜**
- 日柱歧义 → 走 D5 的全拦截分支(与 D3 答「是」同路径)

否决「忽略节气边界」:立春日约 0.3% 用户、节交界日约 3.3% 用户,而生肖屏是 onboarding 的核心 reveal——给错属相是最直接的「不专业」证据,恰好打在 Memorable Thing 上。

## 契约与护栏备注

- **`hour_known` bool flag 是唯一事实源**,不用 00:00:00 哨兵值伪装。哨兵的问题是**没有 flag**,不是有占位值——因此 `birth_datetime` **保持现有 naive ISO datetime 格式不变**(现契约有 `must_be_naive` 校验 + iOS `wallTimeString`,改短格式代价大无收益);`hour_known=false` 时后端统一喂 **12:00 占位**(离两个换日边界最远)
- **`pillars.hour` 的缺失表达必须显式定义**:后端 `Pillars.hour` 与 iOS `let hour: PillarDTO`(`BaziDTOs.swift:71`)当前均非 Optional,消费点有 `PillarsTable.swift:19` / `DualPillarsTable.swift:153-156` / `PromptContextBuilder.swift:52-62`(6 个 `hour_*` key)+ `:216`/`:229`。方案:`hour_known=false` 时响应 `pillars.hour` 置 null,iOS DTO 改 Optional,`PromptContextBuilder` 走 unknown 分支
- **请求契约是 `extra="forbid"`**(`models/bazi.py`):新增 `hour_known` / `late_night` 必须给默认值(`hour_known: bool = True`),否则老客户端 422
- **`calc_rule_snapshot` 必须带 `hour_known`**:`backend/app/core/calc_rule_snapshot.py` 现无此字段,不加则「同一输入永远同一输出 + 快照可审计」被破坏(补时辰前后无法从快照分辨)
- **`ChartPayload` 契约必须一并扩**(2026-09-01 review 新增,原文档漏):每日运势与合盘共用 `DailyFortuneRequest.chart_payload`(`app/models/daily_fortune.py:85`),而 `ChartPayload.day_master_strength` 是 `Literal["weak","balanced","strong","special_pattern"]`(无 `unknown_hour`)、`four_pillars` 必含 `hour` 柱。不扩这两处,无时辰盘**连每日运势请求都发不出去**(422)。iOS 侧对应 `ChartPayloadDTO.from(baziResponse:)`(`DailyFortuneOrchestrator.swift:355-372`)——注意该函数现有 `dayMasterStrength ?? "special_pattern"` 的静默兜底,`unknown_hour` 落进去会被伪装成从格盘,必须显式处理
- **每日运势在一期有明确终态**:一期不做降级 prompt,但**不能留空白**——每日运势是默认落地 Tab(`RootTabView.swift:20` `selectedTab = .dailyFortune`),无时辰用户走完 onboarding 第一眼就是它。一期对无时辰用户走**临时全拦**(与付费墙同款临时态),二期再换降级版
- **content_hash**:`hour_known=false` 时时辰桶不参与,以日期(含 D10 歧义标记)参与
- 改 prompt 模板必须:三边同步校验(`tools/check_prompt_sync.py` PASS)+ evalkit 无 regression + bump `PROMPT_VERSIONS`(CLAUDE.md 双护栏)
- ChartSnapshot payload 加字段(`hour_known` / `late_night` / 歧义标记)必须 `decodeIfPresent`(2026-08-15 老盘 keyNotFound 教训)
