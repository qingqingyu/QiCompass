## 0. 从代码推出的硬约束(不是选择,是事实)

| # | 事实 | 出处 | 对部署的含义 |
|---|---|---|---|

## 1. 部署在哪(2026-11-15 已拍板:Vultr 东京)

### 拍板(2026-11-15):**Vultr 东京**,2 vCPU / 2GB(~$12-14/月)

相对原草案"新加坡 / 阿里腾讯国际站"的三处偏离及理由:

1. **厂商选 Vultr**:命理类 App 不上中国区 App Store(类目受限),主市场为海外
   华人 + 英文用户 → "大陆线路"论点权重归零;Vultr 开通最简(无实名 KYC)、按小时
   计费、快照迁移方便。已知小风险:IP 段声誉一般,出站调 LLM API 偶发风控的概率低,
   遇到换实例即换 IP,零成本。
2. **地域选东京**:受众侧新加坡/东京无感(延迟被 LLM 10-90s 主导);东京对大陆线路
   稍稳,受益者是开发者本人的 ssh 部署/自用体验。
3. **机型 2c2g 而非 2c4g**(用户成本考量,$20/月偏高):内存画像 = 系统+Docker+Caddy
   ~500MB + 2×Python worker(各 300-600MB)= 典型 ~1.2GB(worker ~350MB/个)、上限
   ~1.7GB(≈83%,过 80% 升档判据);典型情形 2GB 有余量。吃紧判据 = `docker stats`
   常驻 80%+,届时快照升档 + 改一条 DNS 记录即可(App 不发版)。AI 走中转链路
   (GLM/DeepSeek),无 Anthropic 直连的地区限制压力(C6 对本仓现状弱化,原则保留)。

### 原草案分析(2026-09-30,存档):新加坡或东京 VPS

理由按权重:

1. **C6 排除大陆和香港**:服务器在大陆/香港直连 Anthropic/OpenAI 不通,只能全程走第三方中转——把模型可用性押在中转商上,且 `ai_provider/ai_model` 缓存身份(ADR-0009)会被中转商静默换模型污染。
2. **不用 ICP 备案**:大陆服务器 + 域名对外提供服务必须 ICP 备案(个人备案周期 2-4 周,且备案主体与"命理"内容有审核风险)。海外节点无此流程。
3. **两个市场都够近**:主受众是华人(简/繁)+ 英文。新加坡/东京到大陆 RTT 约 60-100ms、到台港 30-50ms、到美西 100-150ms。本应用单次请求耗时由 LLM 主导(10-90s),网络 RTT 可忽略。
4. **成本**:2 vCPU / 2-4 GB / 40 GB SSD 的机器 $10-25/月,v1 量级足够(排盘 CPU 很轻,重活都在 LLM 厂商那边)。

候选厂商(同等可用,选熟悉的即可):阿里云国际站新加坡、腾讯云国际新加坡、AWS Lightsail 东京/新加坡、Vultr / DigitalOcean 新加坡。
**大陆用户访问稳定性**:国际站新加坡(阿里/腾讯)对大陆线路通常优于欧美厂商;若后续大陆用户反馈慢,优先换线路而不是换架构。

### 不选的方案

| 方案 | 不选原因 |
|---|---|
| 大陆云(阿里云/腾讯云大陆区) | C6 + ICP 备案,见上 |
| 继续跑在 Mac + 内网穿透(frp / Cloudflare Tunnel) | 家宽断电断网 = 全站下线;付费用户买了解读打不开;Mac 睡眠/重启不可控 |
| Serverless(Cloud Run / Lambda / Vercel) | C1:SQLite + 本地图片需要持久盘;Lambda/Vercel 还有请求时长上限 < 生图 240s |
| Cloudflare 计算层(Python Workers / Containers)(2026-11-14 查证评估) | Python Workers 2026-09 已 GA 且原生跑 FastAPI,但**无本地盘**:SQLite + `images/` 存储层须整体重写为 D1/R2(entitlement/用户/缓存/配额四套全动)——是重写不是部署;Containers 2026-04 GA 但持久卷能力仍在分批 rollout,且 2026-09 披露跨租户数据残留漏洞(退役容器磁盘未擦净),与"钱和账号在盘上"不相容;另有 C3 橙云 100s 超时。**结论:Cloudflare 只承担域名注册 / DNS(灰云)/ R2 备份,计算层不上 CF** |
| Fly.io / Railway / Render 这类 PaaS + 持久卷 | 可行但无明显优势:卷只能挂一台机器,本质仍是单机;亚洲节点和大陆线路一般。若不想碰服务器运维,**这是第二选择** |
| K8s / 多机 | C1 + C4,v1 零收益 |

## 2. 部署形态

```
iPhone ──HTTPS──▶ api.<域名>  (DNS 直接解析,不过 CDN 代理,见 C3)
                     │
              ┌──────┴────────── VPS(东京)────────────────────┐
              │  Caddy :443  (自动签发/续期 Let's Encrypt)       │
              │     │ reverse_proxy,read timeout 360s           │
              │     ▼                                            │
              │  uvicorn app.main:app  容器内 8000 ×2 worker    │
              │     │                                            │
              │     ▼                                            │
              │  /srv/qicompass/data/  (qicompass.db + images/) │
              └──────────────────────────────────────────────────┘
                     │ 每日
                     ▼
               Cloudflare R2(异地备份)
```

### 2.1 进程托管(2026-11-15 拍板:Docker Compose)

**已定 Docker Compose(app + Caddy 两个服务)**:
- 固定 Python 版本 + tzdata(C8)+ 依赖,Mac 上构建和服务器上运行同一镜像,避免"我 Mac 上能跑"。
- 回滚 = 切回上一个镜像 tag。

**备选(未选)systemd + venv + Caddy**:少一层抽象,适合完全不想学 Docker;代价是服务器上 Python/依赖版本要手工管。

两者都是运维工具而非 Python 库依赖,但按 CLAUDE.md「不擅自加依赖」精神在此列出由用户确认(已随 2026-11-15 D3 拍板确认)。

### 2.2 入口:Caddy(已定,随 D3 拍板)vs Nginx

Caddy 一行配置自动 HTTPS + 续期;Nginx 需另配 certbot。无论哪个都必须:
- 读/写超时 ≥ 360s(C3,给 300s iOS 资源超时留余量)
- 请求体上限 1MB 足够(无上传)
- 透传 `X-Request-ID`(已有 middleware 会复用),加 `X-Forwarded-For`
- **uvicorn 端口不对公网暴露**:host 已 env 化(S2 2026-11-18,`UVICORN_HOST`,默认 `0.0.0.0`——容器内绑定正确,Debug 真机连 Mac 也正确)。Docker Compose 形态下 compose 里**不 publish 8000 端口**(仅 `expose`,只留 Caddy 对外 443);systemd 直跑形态生产设 `UVICORN_HOST=127.0.0.1`,唯一入口走本机反代。**注意 `FORWARDED_ALLOW_IPS` 要与之一致**(见 §3)

### 2.3 worker 数、反代头与优雅停机

- `WEB_CONCURRENCY=2`(2 vCPU)。沿用 `run.sh` 结论。
- **✅ proxy-headers 已进 `run.sh`**(2026-10-08):`--proxy-headers --forwarded-allow-ips "$FORWARDED_ALLOW_IPS"`,信任地址经 env 配置(默认 `127.0.0.1`,适合反代与后端同机)。**Docker Compose(反代在另一容器)必须填 compose 网段**——本仓 compose 已固定子网 `172.28.0.0/16`,照抄该值(勿写 Docker 默认池示例 `172.18.0.0/16`,CIDR 永不命中且无报错);compose 对漏配已兜底同值,但显式写错值仍会静默失效。否则 X-Forwarded-For 不被信任,全站匿名用户共享一份每日免费配额。CIDR 网段写法需 uvicorn ≥ 0.31(`requirements.txt` 已锁 `>=0.31,<0.53`;0.27~0.30 会**静默**按字面匹配、网段永不命中)。
- **✅ 优雅停机已落地**(S2 2026-11-18):`run.sh` 传 `--timeout-graceful-shutdown 200`(`UVICORN_GRACEFUL_SHUTDOWN_SECONDS` 可调)——发版重启时让进行中的 LLM 请求(≤150s)跑完,否则用户已扣次数的生成被砍断。Docker 形态 compose 配套 `stop_grace_period: 210s`(>200,防 SIGKILL 抢在宽限期前;两者一起改勿单边调)。(LLM 监控的后台计数任务关停已有 lifespan join,`main.py` `wait_for_pending_records`,不受此项影响。)

## 3. 配置与密钥

生产 `.env` 放服务器 `/srv/qicompass/.env`,`chmod 600`,不进 git、不进镜像。与开发环境的差异:

| 变量 | 生产值 | 备注 |
|---|---|---|
| `JWT_SECRET_KEY` | `openssl rand -hex 32` 新生成 | **绝不能**沿用 `.env.example` 的 dev 值。**轮换影响(C9,2026-10-10 口径)**:登录 JWT 全部失效(用户重新登录)+ 所有已存命盘的 `context_token` 全部 403(iOS 端自动自愈,分模块:深度 403 摄入点就地静默重签、一次/盘/会话;每日清失效 token、下次进入重签;补存入参缺失的老盘与合盘提示重新排盘)——无孤儿化、付费权益不受影响(存服务端 DB),但会造成全用户一波重登录+重排盘,**上线前定好就别动** |
| `QICOMPASS_DB_PATH` | Docker 形态**不配**即默认 `data/qicompass.db`(容器内相对 WORKDIR `/app`,落在 compose 挂载卷 `./data:/app/data` 内);systemd 直跑形态才配宿主绝对路径如 `/srv/qicompass/data/qicompass.db` | 挂载卷内。注意 `.env` 是挂**进容器**消费的(D2 拍板形态),照抄宿主路径容器内不存在 → sqlite 打不开、启动失败 |
| `AI_PROVIDER` / `*_API_KEY` / `*_MODEL` | 生产 key(建议与开发 key 分开,便于按 key 看账单和吊销) | |
| `APP_STORE_*` 5 项 | 真值 | `.p8` 内容整段放 env;**production 缺配任一项会拒绝启动**(2026-10-07 收口,防"Mock 静默放行 = 免费兑换付费权益") |

| `QICOMPASS_FREE_DAILY_LIMIT` | 默认 `150`,可不配 | 免费 module 真烧 LLM 的服务端每日上限/IP+user(2026-10-08 拍板 150,CGNAT 共享出口不挤兑;缓存命中不计) |

## 4. 数据与备份

- **SQLite 保持不变**:v1 流量下单文件 WAL 完全够用,换 Postgres 是 v2 问题(触发条件:需要第二台应用服务器)。
- **data/ 属主(2026-11-21,推前 review 可选项落地)**:镜像以非 root uid/gid 10001 运行(Dockerfile `USER app`),宿主 `./data` bind mount 属主不符时容器内首写 EACCES——首次起容器(及旧 data/ 换新镜像)前执行 `sudo chown -R 10001:10001 ./data`;run.sh 启动自检 data/ 可写,漏做即 fail-fast 并带该指引(不静默降级)。
- **备份**(每日 cron):
  1. `sqlite3 qicompass.db ".backup /tmp/qc-$(date +%F).db"` —— 必须用在线 `.backup`,**不能**直接 `cp`(WAL 模式下会拿到不一致快照)
  2. gzip 后上传 **Cloudflare R2**(2026-11-15 拍板:复用 Cloudflare 账号,免费档 10GB 内、出口免费,不另注册厂商),保留 30 天
  3. `data/images/` 可不备份(丢了按需重生成,仅成本)
- **恢复演练**:上线前至少做一次"新机器 + 最新备份 → 服务起来 → 付费记录还在"。没演练过的备份不算备份。
- 可选增强 Litestream 持续复制(RPO 秒级):**2026-11-15 拍板不引入**(新工具 + 新故障面,v1 每日备份够用)。

## 5. 发版流程(手工,对齐"本地优先 / 不接 GitHub Actions")

> `Caddyfile`(镜像 `qicompass-api:local`,compose `build: .`);`docker build`
> 或 `docker compose build` 均可,镜像仓库仍是可选路径。

```
Mac:  pytest 全绿 → docker build -t qicompass-api:<git sha> → push 到镜像仓库
      (或 rsync 源码到服务器再 build,省一个镜像仓库)
      ⚠ 跨架构:Apple Silicon Mac 的 docker build 默认产出 arm64 镜像;服务器
      若是 amd64(Vultr 常规 VC2 系即 amd64),须
      docker buildx build --platform linux/amd64 --push …(按 S4 实机架构对齐),
      或直接走 rsync 到服务器 build(天然同架构)
VPS:  备份一次 db → 改 compose 里的 tag → docker compose up -d
      → curl https://api.<域名>/api/health 确认 provider/model
      → curl -H "Authorization: Bearer $QICOMPASS_LLM_HEALTH_TOKEN" \
            https://api.<域名>/api/health/llm  (确认监控端点活着)
回滚: 改回上一个 tag → up -d(schema 只 CREATE IF NOT EXISTS,向后兼容回滚安全)
```

发版会造成数秒不可用;v1 可接受(单机零停机需要双实例 + 共享 SQLite,不值得)。

**provider/model 切换**是部署事件(ADR-0010):改 `.env` 重启即可,客户端靠 `/api/health` 身份自动隔离缓存。

## 6. 上线前必须补的代码缺口

### P0:✅ 已落地——生产后端能验沙盒交易(TASK-02,2026-11-01)

> 2026-11-18 复核:S1 全部内容已由 TASK-02 提前完成(11-06 随收编批合 main),
> 本节由"缺口"改记为已完成事实,原文分析存档于下。

- `AppleServerAPIClient` 构造即持 **production + sandbox 双套** client/verifier;`verify_transaction` 生产优先、仅 404 回落沙盒,其他错误不回落(错误显式传播);两环境均 404 → 显式 `AppleVerificationError`
