# 账号删除端点设计决策

> 状态:**四争议点已由外评拍板(2026-11-24),§1/§2 数据清单与删除次序待外评逐行核对后开工**。
> 来源:T20 审核合规纠错(2026-11-23)的首要 P0 待办;2026-11-24 起草,同日外评裁定 §3。

## 0. 为什么必须做(Apple 硬性要求)

**App Store 审核指南 5.1.1(v)**:支持账号创建的 App **必须在 App 内提供发起删除账号的途径**,明文规定「仅提供客服邮箱或网页表单不算数」。QiCompass 有可选 Sign in with Apple / Google 登录(用于跨设备恢复命盘与购买),即适用此条。

- 有登录能力的 App 不提供应用内删除 = **直接被拒风险**(guideline 5.1.1(v) rejection)
- Google Sign-In 使用条款同样要求数据删除能力
- 当前状态:**全部 13 个 API 路由无一 DELETE 方法**,零删除能力

## 1. 数据清单(账号挂钩面,逐表核验于 2026-11-24)

## 2. 端点设计(建议)

### 2.1 契约

```
DELETE /api/auth/account
Authorization: Bearer <jwt>   ← 必须已登录(require_authenticated_user)
```

- 成功 → `200 {"deleted": true, "user_id": "<前 8 位>…"}`(审计用截断显示)
- 未登录 → 401(既有依赖)
- 响应后 JWT 立即失效的建议:**删除后服务端把该 user 的全部签发 token 作废**——当前 JWT 无服务端吊销机制(无 jti 黑名单),MVP 取「删除后 user 不存在,后续所有查 user 的路径自然 404/401」;token 本身剩余有效期内的写路径都先查 user 表 → 已删即拒。**review 点:是否需要显式 jti 黑名单**(我建议 MVP 不做,理由:user 表查无此行即拒绝;重签 token 需 provider 重登,重登时 user 已删会创建新账号——这本身就是正确语义)。

### 2.2 删除次序(事务内)

1. 取 `user_chart_sync` 的该 user 全部 `content_hash`(为 §3.2 的可选缓存清理留原料)→ 删 `user_chart_sync` WHERE user_id
2. 删 `entitlement` WHERE user_id = ?(注意:只删 user_id 命中行;`user_local_id` 轨的行不动——那是设备轨,见 §3.1)
3. 删 `ask_wallet` / `ask_trial_mints` / `ask_purchases` / `ask_history` WHERE owner = ?(owner 含 `user:` 前缀格式)
4. 删 `qicompass_user` WHERE id = ?
5. 删 `free_llm_quota` 的 `user:` 前缀桶(IP 桶保留)
6. **可选(待 review)**:按第 1 步收集的 content_hash 清 `interpretation_cache` / `ask_answer_cache` 关联行——见 §3.2

全部在一个 SQLite 事务(或同库多语句原子提交);失败回滚不半删。

**2026-11-24 外评拍板后的次序修订**(细节见 §3/§5,实施时以此为准):
- 第 2 步 entitlement 改为**匿名化保留**(非删);ask_purchases 同
- 新增:删 ask_history 前反查 ask_answer_cache 清含文本答案;按盘哈希清
  user_input_hash 非空的 interpretation_cache 行 + 合盘模块行
- 新增:删号前先完成 Apple 重认证与 token 吊销(§5.1)
- free_llm_quota 确认在列(bucket user: 前缀)

### 2.3 审计

删除是 irreversible 高危操作,留一行审计日志(操作日志,不落用户数据):`account.deleted user_id=<hash8> tables=<清单> rows=<计数> at=<iso>`——`llm_call_outcomes` 同款 logging 风格(结构化 logger.info)。

## 3. 争议点(**已全部拍板,2026-11-24 外评**)

### 3.1 entitlement 删还是 revoke?→ **拍板:都不——保留匿名化交易台账**

外评否决了我「删了可靠恢复购买重建」的前提:`PurchaseManager.swift:629-630` 自己的注释写着——
消耗型交易 `finish()` 后不再出现在 Apple `Transaction.all`,跨设备恢复的**唯一**凭据就是我方后端账号。
账号删了 = 无处恢复。整行删除还有三伤:退款 webhook 找不到 transaction_id、对账记录丢失、
同笔购买防重复 redeem 失去锚点。

**实施口径**:
- `entitlement` 与 `ask_purchases`:**保留行但匿名化**——`is_active=0` + `revoked_at=now`;
  `user_id` 置 NULL;`user_local_id` 与 `content_hash` 置哨兵值 `"deleted"`
  (**content_hash 可被穷举还原出生信息**——外评 P1-2 同源结论,必须抹);
  只留 transaction_id / product_id / 日期 / environment。
- `ask_wallet`:整行删(消耗余额,删号即失)。
- 确认文案明示「已购章节与问事余额删除后无法恢复」(Apple 允许,只要说清)。

### 3.2 跨用户共享缓存删不删?→ **拍板:纯盘面派生的缓存保留;含用户自输入文本的缓存删**

外评同意纯盘面缓存(interpretation_cache 的无输入行)保留——无 owner 列、同盘他人可复用;
但指出四类缓存**含用户亲手输入的文本**,不是「他人可复用的内容」,应删:

1. **问事答案缓存**(ask_answer_cache):answer 常复述用户问题里的个人处境
2. **M4/M5 章节缓存**:深度解析健康/财富两章存用户自由文本(年龄/当前困扰/资产状况,经 `user_input_hash` 入键)
3. **合盘解读缓存**:含用户填写的对方称呼(name_a/name_b)
4. 相应的 interpret 翻译缓存行(同键派生)

**实施口径**:
- 删 `ask_history` 前先取该 owner 的问题哈希,反查并删 `ask_answer_cache` 对应行
- 从 `user_chart_sync`(与 3.1 保留的 `entitlement.content_hash` 匿名化**前**)取用户盘哈希,
  删 `interpretation_cache` 中这些哈希下 **`user_input_hash` 非空** 的行 + 合盘模块(compatibility_free/paid)的行
- 隐私政策同步:修哈希不可反推句(已于 2026-11-24 修正)+ 加「按盘面标识缓存的解读不与账号关联;你输入的文字随账号删除一并删除」

### 3.3 chapter_feedback 的 client_ip → **拍板:不按账号删,但 IP 匿名化随本任务同批发**

外评同意不按账号删(无 owner 列无法定位),但**否决**了我「独立任务以后再说」的缓办——
否则隐私政策必须一直留着「我们存你的 IP 且无过期时间」这句。

**实施口径**:
- `client_ip` 改存 `HMAC(ip, 服务端密钥)`(去重语义不变——同 IP 同日仍撞同一 HMAC 值);
  密钥复用 JWT_SECRET_KEY 的 HMAC 域分隔派生(与 context_token 同先例),不新增 secret
- 存量行一次性清洗:读原值 → 转 HMAC 回写(或删原值,去重窗口最多损失当日一次)
- 与账号删除端点**同一批上线**

### 3.4 本地数据不捆绑 → **拍板:同意,附三个条件**

外评同意本地数据与账号删除分开,但删除成功后 App 必须:
1. **登出并清 Keychain 登录 token**(否则残留 JWT 还在打已删账号的 API)
2. **本地 entitlement 同步失效**(对齐 3.1 的匿名化口径)——否则界面仍显示章节已解锁,后端已 403
3. 确认文案明示「手机上的命盘会保留」+ 指引「我的 → 重置命盘」想清本机数据的用户

## 4. iOS 侧设计(建议)

- **入口**:「我的」→ 设置区(语言行下方)加「删除账号」行(仅登录态显示——`UserIdentity.isAuthenticated`;未登录不显示,无账号可删)
- **流程**:行点击 → confirmationDialog(红色 destructive 文案「删除账号及云端数据」+ 说明句)→ 确认 → 调 DELETE → 成功 → toast「账号已删除」+ 本地登出(keychain JWT 清除)+ 停止 SyncManager
- **失败**:网络错 → 原有错误 toast;401 → 引导重新登录后再删
- **文案三语**(草案):
  - 行标签:删除账号 / 刪除帳號 / Delete Account
  - 确认标题:删除账号?服务器上的账号数据(已同步命盘、购买记录、问事余额)将被永久删除,无法恢复。本机数据不受影响。/ 刪除帳號?伺服器上的帳號資料(已同步命盤、購買記錄、問事餘額)將被永久刪除,無法恢復。本機資料不受影響。/ Delete account? Your account data on our servers (synced charts, purchase records, question credits) will be permanently deleted. Data on this device is not affected.
  - 确认按钮:永久删除 / 永久刪除 / Delete permanently

## 5. 外评发现的设计遗漏(必须纳入实施)

1. **Sign in with Apple token 吊销(硬性要求,漏了就是 blocker)**:Apple 要求提供 Sign in with Apple
   的 App 在删号时调 Apple REST API 吊销用户 token。当前后端**不存 Apple refresh token**
   (`auth/apple_signin.py` 无相应代码)。建议流程:删号前 App 端先要求用户**重新 Sign in with Apple**
   拿新 authorization code → 后端换 token → 调 Apple revoke 端点 → 再执行删除。需新配 Apple `.p8`
   私钥(secret)。这次重新认证同时封堵「偷来的长效 JWT 可恶意删号」的风险。
2. **free_llm_quota 也要清**:登录用户的 bucket 列存的就是 `user:<id>`,§1 已列但 §2.2 次序确认包含。
3. **不得以客户端上报的 user_local_id 为删除依据**:该值可伪造,按它删 = 能删别人设备的匿名数据。
   只动数据库中**已经与本次 user_id 关联**的 user_local_id 行(entitlement 匿名化时的定位方式)。
