## 0. 为什么必须做(Apple 硬性要求)

**App Store 审核指南 5.1.1(v)**:支持账号创建的 App **必须在 App 内提供发起删除账号的途径**,明文规定「仅提供客服邮箱或网页表单不算数」。QiCompass 有可选 Sign in with Apple / Google 登录(用于跨设备恢复命盘与购买),即适用此条。

- 有登录能力的 App 不提供应用内删除 = **直接被拒风险**(guideline 5.1.1(v) rejection)
- Google Sign-In 使用条款同样要求数据删除能力
- 当前状态:**全部 13 个 API 路由无一 DELETE 方法**,零删除能力

## 2. 端点设计(建议)

### 2.1 契约

```
DELETE /api/auth/account
Authorization: Bearer <jwt>   ← 必须已登录(require_authenticated_user)
```

- 成功 → `200 {"deleted": true, "user_id": "<前 8 位>…"}`(审计用截断显示)
- 未登录 → 401(既有依赖)
- 响应后 JWT 立即失效的建议:**删除后服务端把该 user 的全部签发 token 作废**——当前 JWT 无服务端吊销机制(无 jti 黑名单),MVP 取「删除后 user 不存在,后续所有查 user 的路径自然 404/401」;token 本身剩余有效期内的写路径都先查 user 表 → 已删即拒。**review 点:是否需要显式 jti 黑名单**(我建议 MVP 不做,理由:user 表查无此行即拒绝;重签 token 需 provider 重登,重登时 user 已删会创建新账号——这本身就是正确语义)。

### 2.2 删除次序(事务内)

1. 取 `user_chart_sync` 的该 user 全部 `content_hash`(为 §3.2 的可选缓存清理留原料)→ 删 `user_chart_sync` WHERE user_id
2. 删 `entitlement` WHERE user_id = ?(注意:只删 user_id 命中行;`user_local_id` 轨的行不动——那是设备轨,见 §3.1)
3. 删 `ask_wallet` / `ask_trial_mints` / `ask_purchases` / `ask_history` WHERE owner = ?(owner 含 `user:` 前缀格式)
4. 删 `qicompass_user` WHERE id = ?
5. 删 `free_llm_quota` 的 `user:` 前缀桶(IP 桶保留)
6. **可选(待 review)**:按第 1 步收集的 content_hash 清 `interpretation_cache` / `ask_answer_cache` 关联行——见 §3.2

全部在一个 SQLite 事务(或同库多语句原子提交);失败回滚不半删。

### 2.3 审计

删除是 irreversible 高危操作,留一行审计日志(操作日志,不落用户数据):`account.deleted user_id=<hash8> tables=<清单> rows=<计数> at=<iso>`——`llm_call_outcomes` 同款 logging 风格(结构化 logger.info)。

## 3. 争议点(请 review 者逐条拍板)

### 3.1 ⚠️ entitlement 删除 = 购买丢失?

删除账号后 entitlement 行被删。用户重新登录(同 Apple ID)并恢复购买:
- `Transaction.all` / receipt 校验可重新拉回历史交易 → webhooks/redeem 重建 entitlement → **购买可恢复**
- 但**未购的消耗型问事余额**(ask_wallet 余额来自次数包)是消耗语义,Apple 不提供恢复凭据——删号即失,**这是账号删除的预期语义**(用户主动要求删数据)
- **风险**:用户删号后重登,深度命书模块显示未购 → 以为丢了已付款内容 → 差评/退款请求
- **缓解选项**:
  - A. 删 entitlement 时**不删**,只 revoke(`revoked_at` 填时间、`is_active=0`)——重登恢复购买时 revoke 行如何处理需定义(恢复时按 transaction_id 幂等 upsert,revoked 行复活?)——语义复杂化
  - B. **全删**(我倾向):账号删除 = 数据清零,Apple 审核语义如此;恢复购买链路已验证可重建;问事余额属消耗型,丢了合理
  - **review 请拍板 A/B**

### 3.2 interpretation_cache / ask_answer_cache(跨用户共享缓存)

- 两表按 content_hash/问题哈希寻址,**同盘的多用户共享同一行**。删一个人的账号不该删别人的缓存行。
- 但缓存行内容(解读全文)确实由该用户的出生数据派生。隐私视角:哈希不可逆推出生数据(已写入隐私政策)。
- **选项**:
  - X. **不删**(我倾向):非账号挂钩数据(无 owner 列),Apple 删除要求针对「account + associated data」;内容寻址缓存属服务端基础设施,同匿名用户生成的行无差别
  - Y. 按用户 content_hash 删:更彻底,但会删掉其他同盘用户的热缓存(体验损害);且哈希→行的映射要先查 user_chart_sync(第 1 步已收集)——技术上可行
  - **review 请拍板 X/Y**(隐私政策 v0.2 §4 现文写的是「缓存……如你希望删除:联系我们」——若拍 X,政策措辞要改为「缓存按内容寻址、跨用户共享,不随账号删除清除」)

### 3.3 chapter_feedback 的 client_ip

- 无 owner 列,只有 content_hash + client_ip。账号删除时**无法**按账号定位这些行。
- IP 属个人数据(GDPR 口径)。选项:
  - P. **不动**(现状;隐私政策已披露存 IP;Apple 审核问的是账号删除,不是 IP 生命周期)
  - Q. 删除时顺带把该 user 常用 IP 的反馈行删除/脱敏(误伤共享 IP 用户;且「常用 IP」要先从 ask_trial_mints 收集)
  - **review 请拍板 P/Q**(我倾向 P + 后续独立任务:IP 定期脱敏/截断)

### 3.4 未登录用户的本地数据

账号删除只清服务端。App 本地(SwiftData 命盘/问事会话簿/缓存)已有「重置全部数据」。**iOS 删除流程建议**:删除账号 sheet 里明说「服务器上的账号数据(含已同步命盘与购买记录)将被删除;本机数据不受影响,可在『我的 → 重置全部数据』单独清除」——两条路径分开,不捆绑。

## 4. iOS 侧设计(建议)

- **入口**:「我的」→ 设置区(语言行下方)加「删除账号」行(仅登录态显示——`UserIdentity.isAuthenticated`;未登录不显示,无账号可删)
- **流程**:行点击 → confirmationDialog(红色 destructive 文案「删除账号及云端数据」+ 说明句)→ 确认 → 调 DELETE → 成功 → toast「账号已删除」+ 本地登出(keychain JWT 清除)+ 停止 SyncManager
- **失败**:网络错 → 原有错误 toast;401 → 引导重新登录后再删
- **文案三语**(草案):
  - 行标签:删除账号 / 刪除帳號 / Delete Account
  - 确认标题:删除账号?服务器上的账号数据(已同步命盘、购买记录、问事余额)将被永久删除,无法恢复。本机数据不受影响。/ 刪除帳號?伺服器上的帳號資料(已同步命盤、購買記錄、問事餘額)將被永久刪除,無法恢復。本機資料不受影響。/ Delete account? Your account data on our servers (synced charts, purchase records, question credits) will be permanently deleted. Data on this device is not affected.
  - 确认按钮:永久删除 / 永久刪除 / Delete permanently
