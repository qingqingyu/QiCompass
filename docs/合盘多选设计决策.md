# 合盘多选改造设计决策

Generated on 2026-08-13（grill-me 会话锁定）
Status: ACCEPTED（待实施）
关联文档: `bazi-app-design-doc.md` / `MONETIZATION.md` / `DESIGN.md` / `CLAUDE.md` / `命理引擎设计决策.md`

## 背景

现状合盘（Tab 3）是 1 对 1：A盘（你）单选 + B盘（对方）单选（存档或临时输入）→ 点"开始合盘" → 单份详情页（双盘对比 + 4 评估卡 + 流年同步 + AI 解读）。

用户诉求：B盘只能选一个人不满足需求，希望**一次选多个对方**，且**结果按不同的人逐个查看**。本页交互需要重新设计。

## D1 交互形态（用户确认）

- 配置页：A盘（你）单选不变 + **B盘改为多选名单**
- 点"开始合盘"→ **结果列表页**：每个对方一张卡片
- 点卡片 → 该对完整详情（复用现有 `CompatibilityMainView`：双盘对比 + 4 评估卡 + 流年同步 + AI 解读）
- A盘不搞多选（矩阵 N×M 复杂度和付费模型都爆炸，v2 再说）

## D2 对方名单模型（用户确认）

名单成员两种来源自由混排：

1. **存档勾选**：从 UserSnapshotLink 池勾选（A盘自己除外）
2. **临时输入**：手动填出生信息（复用现有 tempInputForm 字段），**可加多个**（如"相亲对象甲/乙/丙"）

**上限 8 人**（我拍板，理由）：全局免费池 10 次/天，8 对方全看 AI = 8 次，不触顶；同时防呆控制批量计算时长（8 次串行 ≈ 秒级）。

## D3 计算时机（用户确认）

- 点"开始合盘" → 串行循环跑 N 次 `/api/bazi/compatibility`（确定性定性评估，free 部分），UI 显示 i/N 进度
- **AI 解读不进批量**。点进某对详情页 → 用户点"生成解读"才触发（复用现有按钮 + 付费墙 + 次数逻辑，零改动）
- 理由：确定性便宜且是"即时可看的免费价值"；AI 贵且必须用户主动触发（对齐 2026-08-01"β 点击触发 + cost control"决策）

## D4 付费与次数（用户确认，现有模型零改动）

- **付费**：每对 $11.99，entitlement 按 `compatibilityHash` 绑定（现有模型天然如此）。买"和甲"的解读不影响"和乙"的免费部分；用户可只买真正关心的那对
- **次数**：每对的 AI 解读各自扣全局池 1 次（缓存命中不扣）。5 对全看 = 5 次/天
- 定性摘要列表完全免费、不消耗次数
- **打包价（一次会话 N 对一个价）明确不做**：需要新 product_id + entitlement 绑定逻辑改 + 定价难题（2 对 vs 8 对怎么定），等 v1 真实转化数据再设计

## D5 跨启动恢复（用户确认方向）

- 进合盘 tab 默认显示**上次的结果列表**，纯本地恢复，不调 API
- 持久化到 UserDefaults：

| Key | 内容 |
|---|---|
| `compat.lastPersonAHash` | 上次 A 盘 contentHash（失效则 fallback 最新 link） |
| `compat.lastContext` | 上次 context（默认 "general"） |
| `compat.roster` | 名单 = JSON `[personBHash]`（临时人用 resolved contentHash） |

- **恢复列表 = 已算对 ∩ 名单**：`CompatibilitySnapshot` 按 (personAHash == A, context == C) 查，再按名单过滤、createdAt DESC 排序
- 名单过滤的意义：用户在配置页删掉的对方，重启后不会从快照库"复活"；快照本身保留（内容寻址可回溯，重新勾选秒回）
- 恢复时清理无效名单项：link 被删 / ChartSnapshot 不存在的 hash 从名单剔除（防脏数据）
- 首次使用（0 已算对）自然落到现有 `.empty` / 配置页流程

## D6 临时人持久化（我拍板：不建 UserSnapshotLink）

现状注释明确"模式 B 隐式落地**不写** link 是有意为之"（对方不是"我自己"，不污染命盘列表）。多选下**保持不建 link**，理由：

1. 零 SwiftData schema 演化（项目对 schema 演化保守：CLAUDE.md"不用 VersionedSchema"、iOS 17.2 @Relationship crash 史）
2. 零 SyncManager 影响（link 会被 push 上云，临时人上云是脏数据）
3. ProfileView「我的命盘」/命主卡零改动（不用过滤 isTemporary）

**显示名策略**：
- 会话内：临时表单加**可选"称呼"字段**（默认空），填了就显示称呼
- 跨启动：显示兜底名 `"对方" + 出生日期`（从 ChartSnapshot.birthSolarTime 读）
- 临时人落地 ChartSnapshot（无 link，现状行为）；第一次计算后其 resolved contentHash 写入名单（D5）

## D7 增量计算（我拍板）

点"开始合盘"时对每对先本地预查：

- 存档对方：`CompatibilitySnapshotStore.get(canonicalKey(aHash, bHash, context))` 命中 → 跳过 API 直接用本地
- 临时对方：resolvedHash 已知（曾算过）→ 同样预查；内容寻址的自然收益——重输同生日临时人命中同一 contentHash，秒出

只有未命中（新增对 / 换 context）才调 API。改名/改勾选后重算 = 只算新增。

## D8 context 作用域（我拍板）

- context（general/marriage/business）保持**配置页全局**：一次合盘一个 context，N 对共用
- 恢复列表按 (A, context) 查（hash 含 context，语义自然）
- 换 context = 回配置页改 → 增量重算（新 context 对全部未命中 → 全调 API，确定性便宜可接受）
- 不做 per-pair context（列表卡片会一 B 多卡，混乱；v2 再说）

> **2026-08-16 调整（用户决策）：维度 picker 整体移除，context 固定 `"general"`。**
> 原因：① context 参与 `compatibilityHash` 且 entitlement 按 hash 绑定 → 同一对人换维度要重新付 $11.99，维度事实上成了付费粒度，不合理；② 「婚姻/事业」预设与 2026-08-14「两人磁场是否合拍」单轨定位（不预设关系类型）矛盾。
> 落地：数据层 / 后端契约 / `CompatibilitySnapshotStore.list(personAHash:context:)` 全保留，仅客户端源头固定（`CompatibilityViewModel.context` 改 `let`，restore 不再恢复持久化 context，配置页 picker 删除）。历史非 general 快照仍在库中但不再恢复展示；`compat.lastContext` 键下次 save 覆写为 general。

## D9 列表卡片内容（我拍板）

每张卡片：

- 对方名（alias / 临时称呼 / 兜底名）
- 出生日期 + 日主
- 定性摘要两句话：**五行互补** + **日主关系**（四维里最有信息量的两维；生肖匹配、地支合冲进详情看）
- **"已解读"标记**：`CompatibilitySnapshot.interpretation != nil` 时显示（用户快速知道哪对已经生成过 AI）
- 不给数字分（既有决策，不变）

## D10 状态机与错误隔离（我拍板）

`CompatibilityViewState` 从单结果改为：

```
loading → empty → configuring（名单编辑）→ computing(completed, total)（批量确定性）
        → list([PairSummary])（结果列表）
        → detail(PairSummary, response, interpretState)（单对详情，复用现有 ready 逻辑）
failed 保持整体态（列表加载失败等系统级错误）
```

- **对级错误隔离**：批量计算中某对失败 → 该卡片显示失败态 + "重试"（单对重调 API），不拖垮整个列表。对齐现有"AI 失败隔离"哲学（阶段 1 失败也隔离，不再整体 failed）
- 批量串行（Task 循环 await，N≤8 秒级完成），不做并发（后端 CPU-bound，串行更稳、日志更清晰）
- 详情态复用现有 `CompatibilityMainView` + generateInterpretation 全流程（缓存查询 → 次数 → API → 禁词扫描 → 缓存写入），**零改动**

## D11 增删入口（我拍板）

- **结果列表纯展示**（无滑动删除），toolbar「编辑名单」→ 配置页
- 配置页预填：A盘 = 持久化 A、勾选态 = 当前名单、context = 持久化 context
- 增删只在配置页发生：勾/反勾存档、添加/移除临时人
- **删除 = 从名单移除**（快照保留可回溯）；重算后列表 = 名单 ∩ 已算对
- 单一入口的理由：状态一致性简单（列表 = f(名单)，无第二处修改点）

## D12 后端（我拍板）

**零改动**。后端已是无状态 1 对 1 接口（模式 A/B 双分支），多选 = 客户端循环调 N 次。付费拦截、entitlement、缓存键全部按单个 compatibilityHash 设计，天然兼容。

## D13 边界态（我拍板）

| 场景 | 行为 |
|---|---|
| 0 存档 | `.empty`（现有 CompatibilityEmptyView，引导去深度解析） |
| ≥1 存档但对方池空（只有自己） | 配置页对方池显示"暂无对方命盘" + 引导：临时输入 or 去「我的」新建命盘 |
| 名单为空点"开始合盘" | 校验拦截："请至少选择一位对方" |
| 持久化 A hash 失效（link 被删） | fallback 最新 link |
| 持久化名单含无效 hash | 恢复时静默剔除 + 清理 |
| 批量计算中切 tab | Task cancel（现有 computeTask?.cancel 语义保持） |

## 影响文件清单

**改**：
- `Features/Compatibility/CompatibilityView.swift` — 状态机扩为 list/detail 两态 + NavigationStack push 详情
- `Features/Compatibility/CompatibilityViewModel.swift` — 名单（roster）管理 + 批量计算 + 增量预查 + UserDefaults 持久化
- `Features/Compatibility/CompatibilityConfigView.swift` — B盘区改多选名单 UI + "添加临时对方"入口（复用现有 tempInputForm，加可选称呼字段）
- `Services/CompatibilitySnapshotStore.swift` — 加 `list(personAHash:context:)` 查询
- `Features/Compatibility/ChartArchivePickerView.swift` — 单选改多选（或新增多选变体）

**新**：
- `Features/Compatibility/CompatibilityPairListView.swift` — 结果列表 + 卡片（PairSummary: status 机算/失败态）
- 名单持久化小工具（UserDefaults 读写，可放 VM 内）

**不动**：
- `CompatibilityMainView`（详情页复用）、`CompatibilityOrchestrator`（单对流程复用）、后端全部、`MONETIZATION.md`、entitlement/付费墙/计数器

**测试**：VM 批量逻辑（对级错误隔离 / 增量预查 / 名单过滤恢复）+ 名单持久化 round-trip

**i18n 注意**：合盘 UI 现状为中文硬编码（i18n plan Slice 3 才覆盖），新 UI 文案跟随现状，Slice 3 统一补 key。

## 不做（v2+ / 明确砍掉）

- 打包价 SKU（等 v1 转化数据）
- A盘多选矩阵（N×M）
- per-pair context
- 结果列表滑动删除（配置页统一管理）
- 临时人一键转正式存档
- 纯游客合盘（A盘也临时输入）——既有 v2 决策，不变

## 风险

| 风险 | 缓解 |
|---|---|
| 8 次串行 API 秒级等待 | i/N 进度条 + 串行保稳；上限 8 防呆 |
| 名单（UserDefaults）与快照库不一致 | 恢复时过滤无效 hash + 自动清理（D5） |
| 全局池 10 次/天 vs 8 对方全 AI = 8 次 | 8 人上限是配套决策；缓存命中不扣，重看不耗 |
| 临时人跨启动显示名降级为"对方+日期" | 可接受（会话内称呼已覆盖主要场景）；v2 若反馈强烈再做临时人 alias 持久化 |
